## 2. 현재 데이터로 새 p99나 권장 초수를 산출하지 않은 이유

source #3의 admission·후속·C 점검에서 기록이 닫힌 18개 시행을 다시 읽었다. **180초 wall-time timeout 없이 종료한 것은 15건**이고 그중 정답은 14건, 의미적 실패는 1건이다. 나머지 3건은 180초 뒤의 진행을 관측하지 못했다. 이것은 실험 집단을 합친 새 성공률이 아니라 예산 감사를 위한 기록 재고다. 원실험의 지표·분모·무효 판정은 유지한다. 재계산 자료 (operator-local source withheld)

고정 관측 종료 뒤의 사건 시간을 모르는 구조는 우측 검열이다. 여기서는 NIST의 설명을 과제 종료 시간 관측에 적용했다. 시간이 잘린 시행에 180초를 ‘실제 완료 시간’으로 넣거나, 완료된 사례만 남겨 지연 분포를 만들면 다른 질문에 답하게 된다. [NIST: Censoring](https://www.itl.nist.gov/div898/handbook/apr/section1/apr131.htm)

이 18개는 과제·arm·계정 시기·동시성이 섞여 있고 같은 사례를 반복 포함한다. 본실험은 첫 무효 뒤 중단돼 뒤의 계획 셀도 없다. 독립적이고 대표적인 서비스 요청 표본이 아니므로 p95·p99·p99.9나 더 긴 한도에서의 성공률을 추정하지 않았다. 모집단 포함 비율과 추정의 신뢰수준은 표본 내 최대값과 별개라는 점도 고려했다. [NIST: 비모수 tolerance interval](https://www.itl.nist.gov/div898/handbook/prc/section2/prc264.htm)

현재 수행한 계산은 **실제 종료 시각을 절단점으로 삼은 기록 집계**다. 에이전트 재실행이나 Monte Carlo 예측이 아니다. 관측되지 않은 180초 이후 시간을 임의 분포로 생성하는 시뮬레이션은 하지 않았다.

## 3. 서비스 SLO, 호출 제한, watchdog의 근거는 다르다

| 대상 | 정해야 하는 내용 | Jev 연구에서의 현재 상태 |
|---|---|---|
| 사용자 과제 SLO | 무엇을 성공이라 부르는지, 어떤 작업군인지, 시작·최종 전달 시각, 허용 지연·성공 비율·보고 기간 | 실제 사용자 요구에 근거한 수치 미정. 기존 180초를 SLO로 다시 이름 붙이지 않음 |
| 개별 모델·도구 호출 제한 | 연결·DNS/TLS·대기·응답 중 포함 구간, 허용 오탐 timeout, 상위 남은 시간, 취소 책임 | 직접 판정 패널의 Astra 180초·Jev 60초는 root 전체 180초와 다른 시계 |
| root 전체 실행 제한 | root·도구·판정·수정 중 포함 범위, 단계/호출 상한과의 관계, 종료 시 상태 | 현행 180초. 검증·수정도 같은 시간을 소비 |
| 바깥 실행기·정리 한도 | 초기화·실행·증거 저장·정리 각각의 한도와 강제 종료·잔존 작업 처리 | Harbor agent 210초 등 여러 한도 존재. 차이 30초가 실측으로 충분하다고 확인된 것은 아님 |

Google SRE는 사용자에게 중요한 사건과 측정 기간·분모를 정의하는 데서 SLO를 시작한다. AWS의 0.1% 허용 오탐과 p99.9 예시는 같은 Region의 하위 호출을 위한 방법 설명이다. 이를 다단계 agent의 전체 시간으로 옮길 수 없다. gRPC는 하위 호출에 남은 deadline을 전달하고, 만료 뒤 실제 작업 취소를 처리할 책임을 구분한다. 이것은 적용할 설계 원칙이며 GEODE가 gRPC의 보장을 사용한다는 뜻은 아니다. [Google SRE](https://sre.google/workbook/implementing-slos/), [AWS 원문](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf), [gRPC Deadlines](https://grpc.io/docs/guides/deadlines/)

문헌을 현재 다단계 실행에 적용한 **설계상 추론**으로는, 한 호출의 p99를 여러 단계에 그대로 복사하거나 단계별 p99를 더해 전체 p99라고 부를 수 없다. 단계 간 의존과 공유 부하, 조건부 수정 횟수, 병렬 구간의 최대 지연을 함께 봐야 한다. Google의 *The Tail at Scale*은 구성요소의 드문 지연이 결합될 때의 영향을 설명하지만, 검색 fan-out의 복제 요청 기법을 현재 agent 실험에 추가하는 근거는 아니다. [Dean & Barroso, 2013](https://barroso.org/publications/TheTailAtScale.pdf)

## 4. 한도 변경은 행동을 바꿀 수 있다

도입 이력을 추적한 범위에서는 root 6라운드·180초와 host 210초가 2026-09-21 초기 파일럿의 운영 계약에서 시작해 Harbor 경로로 이어졌다. 범용 AgenticLoop 설정의 기본값은 rounds=0/time=0이므로 180초가 프레임워크 기본은 아니다. 패널 180/60초는 9월 26일에, 이를 재사용한 Score 제한은 9월 27일에 도입됐다. 정체 방지 동기는 확인했지만 **이 수치를 지연 계측이나 SLO에서 산출한 근거는 확인한 파일·커밋 범위에서 찾지 못했다.** 모든 과거 자료에 근거가 없다는 전역 주장은 아니다. 고정 커밋·행·검색 범위 (historical operator-local reference; source path withheld)

현재 GEODE 소스는 전체 time budget에서 `min(300, budget/3)`을 검증·수정용 reserve로 계산한다. 남은 시간이 headroom 아래이면 도구를 끄고 후보 제출을 요구하며, 총예산과 reserve를 실행 안내에 넣는다. 따라서 180초를 바꾸면 취소 시각뿐 아니라 프롬프트와 도구 사용 시점도 바뀔 수 있다. 실제 계산과 소비 위치 (operator-local source withheld)

후속 실험에서 예산을 바꾼다면 이를 **시간 예산 정책 변경**으로 명시해야 한다. ‘다른 것은 전부 그대로이고 대기만 늘렸다’고 표현할 수 없다. 순수한 종료 한도의 효과와 안내·reserve의 효과를 분리하려면 현재 결합을 먼저 설계 차원에서 구분해야 하며, 이는 별도 소스 변경·검증 범위다.

Anthropic은 동일 모델·하네스·과제에서 자원 설정을 바꾸어 평가 점수와 인프라 오류가 달라지는 현상을 보고했다. 이 보고의 주된 변수는 CPU·메모리이므로 배수를 시간에 적용하지 않는다. 채택할 점은 **자원 조건과 그 집행 방식도 평가 변수이며, 오류 감소와 실제 수행 기회 증가를 구별해야 한다**는 것이다. [Segato, 2026](https://www.anthropic.com/engineering/infrastructure-noise)

## 6. 다음 예산 결정에 사용할 절차

아래는 이번 문헌·소스·관측을 결합한 **설계 제안**이다. 기존 실험에 이미 구현되거나 승인된 정책이 아니다.

1. **질문을 먼저 선택한다.** 동일 서비스 deadline 안의 유용성을 보려는지, 충분한 계산 기회에서 판정기의 품질과 비용을 보려는지 구분한다. 두 결과를 원하면 서로 다른 실험 조건으로 보고한다.
2. **시간 경계를 명세한다.** root 시작→최종 전달, 호출 시작→응답, setup·저장·정리 시간을 분리한다. 단계/토큰/호출 수 상한과 시간 상한 중 어느 것이 먼저 실행을 자를 수 있는지 기록한다.
3. **새 보정 자료를 분리한다.** 현재 실패 사례는 문제를 찾은 진단 자료다. 새로운 한도 선택에 쓰면 후속 주장의 독립 평가 자료와 분리하고, 기존 원본을 새 조건 결과와 섞지 않는다.
4. **후보 정책과 선택 규칙을 먼저 고정한다.** 외부 기본 초수를 복사하지 않고, 독립적인 pilot의 단계별 관측과 작업 구조를 사용한다. 허용 timeout·비용·성공 trade-off, 추가 예산의 효용이 줄어드는 기준, 최대 보정 비용과 미결정 종료 조건을 결과를 보기 전에 정한다. 구체 수치는 아직 미정이다.
5. **비교 arm에 같은 정책을 적용한다.** 어려운 arm만 연장하지 않는다. 계정·부하·시간대·순서·동시성을 기록하고, 한도 변경에 따라 바뀌는 안내·reserve도 동결한다.
6. **시간별 정답·비용·중단 원인을 같이 보고한다.** 최종 정답을 verifier로 확인하고, timeout·의미 실패·전송 실패를 분리한다. 한도를 늘렸을 때 점수가 오르더라도 원래 180초 조건의 결과를 대체하지 않는다.
